# 건강 기록 → 모험 → 길드 성장 사용자 여정 (레거시 기록)

## 완료 범위

익명 사용자가 식단·운동·수분을 기록하면 서버가 이를 한 번만 저장하고, 현재 건강
상태와 HBI를 갱신한다. 가장 최근에 끝난 UTC 12시간 구간은 70% 효율의 자동 모험으로
정산되며, 확정된 던전 규칙에 따라 5개 방 경로와 탑 층수가 함께 저장된다. 보상 수령
시 20%는 훈련장에 자동 투자되고 나머지는 보유 길드 주화가 된다.

```text
익명 ID(최대 36자)
  → 건강 기록 + 클라이언트 UUIDv4
  → activity_logs PK로 중복 차단
  → 오늘 상태/HBI 갱신
  → 완료된 12시간 모험 1회 정산
  → 전투 … 휴식/상점 → 보스, 총 5개 방 저장
  → 보상 1회 수령
  → 훈련장 20% 자동 투자 + 주화 80% 보유
```

## 건강 기록 멱등성

- Flutter는 한 번의 기록 시도에 UUIDv4를 만들고 `idempotency_key`로 전송한다.
- 응답을 받지 못한 동일 입력을 다시 시도하면 같은 UUID를 재사용한다.
- 서버는 UUID를 `activity_logs.activity_id`에 저장해 재시작·다중 프로세스에서도 DB
  기본 키로 최종 중복을 막는다.
- 같은 UUID와 같은 내용은 기존 결과를 `duplicate=true`로 반환한다.
- 같은 UUID를 다른 사용자·종류·값·세부 데이터에 재사용하면 `409`로 거절한다.
- 이전 인메모리 멱등성 후보는 canonical runtime에서 제거했다.

## 실제 모험 콘텐츠

- 방 수: 5
- 첫 방: `COMBAT`
- 마지막 방: `BOSS`
- 보스 직전: `REST` 또는 `SHOP`
- 중간 방: 전투 50 / 이벤트 15 / 휴식 15 / 상점 10 / 정예 10
- 모험 ID의 SHA-256 바이트를 사용해 방을 결정하므로 재조회 결과가 바뀌지 않는다.
- 낮은 HBI에서도 손실·음수 보상·기존 성장 회수는 없다.

## 식단 기록 UX

식사 종류와 칼로리뿐 아니라 탄수화물·단백질·지방·식이섬유를 직접 입력하고
`detail_data`에 저장한다. 숫자와 음수 여부를 앱에서 검증하며, 실제 지급량이 cap과
anti-farming에 따라 달라질 수 있으므로 고정 Exp 지급 문구를 제거했다.

## 검증

- 건강 기록 동일 UUID 재시도 1회 저장
- UUID를 다른 payload에 재사용할 때 409
- 식단·운동·수분 → 상태 집계 → HBI → 모험 → 보상 → 훈련장 전체 SQLite 통합 테스트
- 5개 방의 첫 방·보스 직전·마지막 방 규칙과 재조회 일관성
- Flutter 실패 후 재시도 UUID 재사용
- 길드 화면의 탑 층수·5개 방 경로·보상·훈련장 위젯 테스트
- 실제 로컬 Flutter Web + 격리 SQLite API 수동 확인

## 운영 안전선과 잔여 범위

- DB migration과 실제 Supabase 데이터 변경은 없다.
- 기존 37자 로컬 익명 ID는 API 호출 전에 36자로 한 번 정규화한다. 37자 ID는 canonical
  PostgreSQL 컬럼에 저장될 수 없었으므로 운영 건강 기록을 잃는 변환은 아니다.
- 앱 종료를 넘는 오프라인 기록 큐, 과거 여러 모험 구간 자동 회수, 실제 전투 수치와
  모험 회상 화면은 다음 확장 범위다.
